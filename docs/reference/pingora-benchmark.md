# Pingora 性能实测

2026 年 11 月 20 日，从 US-A 对运行 OpenFlare Edge `0.1.8` 的 JP-B 和 US-C 进行测试：公网直连测量访问延迟与下载速率，隔离实例对照测量 WAF 的吞吐和 CPU 开销。

## 测试环境与性能策略

| 代号 | 角色 | CPU | 实际 Pingora 工作线程 | 实际空闲回源连接池（每工作线程） |
| --- | --- | --- | ---: | ---: |
| US-A | 压测客户端 | 1 vCPU | — | — |
| JP-B | Edge 节点 | 3 vCPU，ARM64 | 3 | 192 |
| US-C | Edge 节点 | 1 vCPU，x86-64 | 1 | 64 |

两台 Edge 使用同一份策略，`threads_auto` 开启。策略中的手动值为 1 个工作线程、每线程 128 个空闲回源连接；自动模式覆盖这两项，表中实际值来自压测实例的启动日志。

| 类别 | 两台 Edge 的共同配置 |
| --- | --- |
| 运行时 | 开启工作窃取；每个监听文件描述符 1 个监听任务；备用定时器关闭 |
| 下游 HTTP/2 | 通过 TLS 协商 HTTP/2，关闭 h2c；每条连接最多 100 个并发流；流和连接的初始窗口各为 1 MiB；最大帧 16 KiB，最大头列表 32 KiB，头部表 4 KiB，发送缓冲区上限 256 KiB |
| 监听与连接复用 | TLS 卸载线程池、`SO_REUSEPORT`、TCP Fast Open、监听端 TCP Keepalive 均关闭；TCP 收发缓冲区使用系统默认值；未设置长连接请求数上限和下游 HTTP/2 空闲超时 |
| 反向代理缓存 | 节点缓存开启；内存 128 MiB、磁盘 512 MiB，单对象上限 16 MiB；磁盘并发读/写上限 32 / 16，非活跃清理阈值 48 小时；缓存锁等待 5 秒、最多重试 1 次 |
| 回源 | HTTP/1.1；连接、总建连、读取、写入、空闲超时分别为 3 / 8 / 30 / 30 / 60 秒；最多重试 3 次；验证源站证书和主机名 |

测试资源由本地 Pages 直接提供，未经过反向代理缓存或上游服务。公网延迟与下载基线使用完整 WAF 和 50 请求/秒/IP 的站点请求频率限制；隔离 WAF 对照关闭该限制，保留相同的性能策略与访问日志。

## 公网直连

客户端直接连接节点公网 IP，不经 DNS 解析或 Cloudflare。HTTP `Host` 和 TLS SNI 仅用于匹配 Pages 站点和证书。两端使用相同的 923 B 静态文件；下载测试另用 30 MiB 的本地 Pages 文件，均无上游请求。

| 指标 | JP-B | US-C |
| --- | ---: | ---: |
| ICMP 平均 RTT（5 次） | 115.7 ms | 1.0 ms |
| HTTP/1.1 长连接 P50 / P95（40 请求/秒） | 117.3 / 121.4 ms | 3.5 / 4.9 ms |
| HTTPS / HTTP/1.1 长连接 P50 / P95（40 请求/秒） | 117.7 / 120.2 ms | 3.8 / 6.9 ms |
| HTTPS / HTTP/1.1 新建连接 P50 / P95（5 请求/秒） | 354.3 / 363.9 ms | 10.7 / 14.2 ms |
| HTTPS / HTTP/2 下载 30 MiB，三次端到端速率中位数 | 111 Mbps | 775 Mbps |
| 同一下载，首字节后传输速率中位数 | 131 Mbps | 826 Mbps |

延迟计至完整响应接收结束。HTTP 和 HTTPS 长连接测试均使用 12 条连接，分别调度 560 和 640 个请求，全部完成；新建 HTTPS 连接测试使用 5 路并发，调度 60 个请求。新建连接包含 TCP 和 TLS 建连，未预热的长连接样本也包含首次建连。下载使用单连接，端到端速率按文件比特数除以总耗时计算。

## WAF 对照

隔离实例使用各节点本机的 Edge 二进制。客户端通过点对点私有网络直连实例 IP。三组均使用相同的 Pages 文件，测试站点没有绑定额外的站点级 WAF 规则组。

| 组别 | 生效策略 |
| --- | --- |
| 完整 WAF | 全局 IP 匹配与「平衡」攻击检测 |
| 仅 IP 匹配 | 保留全局 IP 匹配，移除攻击检测步骤 |
| 关闭 WAF | 移除测试实例中的所有 WAF 规则组 |

在 US-A 上使用 `h2load`（nghttp2 `1.68.0`），每组预热 2 秒、采样 6 秒。主对照使用 8 条连接、每条最多 16 个在途 HTTP/2 流，按正序和反序各跑一轮，以下吞吐为两轮实际收到的 HTTP `200` 响应数除以 12 秒。另以 16 条连接、每条 24 个流测试吞吐是否继续增长。固定负载为每条连接 20 请求/秒，共 160 请求/秒。

| 节点与指标 | 完整 WAF | 仅 IP 匹配 | 关闭 WAF |
| --- | ---: | ---: | ---: |
| JP-B：成功吞吐，8 × 16 | 419.5 请求/秒 | 486.1 请求/秒 | 488.0 请求/秒 |
| JP-B：成功吞吐，16 × 24 | 415.8 请求/秒 | 445.0 请求/秒 | 489.8 请求/秒 |
| JP-B：160 请求/秒，P95 | 126.9 ms | 123.4 ms | 120.5 ms |
| JP-B：160 请求/秒，Edge CPU | 32.2% | 12.1% | 10.2% |
| US-C：成功吞吐，8 × 16 | 273.8 请求/秒 | 255.7 请求/秒 | 283.1 请求/秒 |
| US-C：成功吞吐，16 × 24 | 280.8 请求/秒 | 261.3 请求/秒 | 255.8 请求/秒 |
| US-C：160 请求/秒，P95 | 21.9 ms | 5.0 ms | 5.8 ms |
| US-C：160 请求/秒，Edge CPU | 25.7% | 9.4% | 8.7% |

CPU 为固定负载期间服务 cgroup 的 2 秒采样均值，以单个 vCPU 的满载为 100%。固定负载下，每台节点的每组均收到 960 个 HTTP `200`，表中的延迟只统计 HTTP `200` 响应。

::: details 8 × 16 对照的分轮 HTTP 200 响应数

| --- | ---: | ---: | ---: |
| JP-B，第 1 轮 | 2,546 | 2,895 | 2,871 |
| JP-B，第 2 轮 | 2,488 | 2,938 | 2,985 |
| US-C，第 1 轮 | 1,671 | 1,516 | 1,759 |
| US-C，第 2 轮 | 1,615 | 1,552 | 1,638 |

## 结果解读

- **攻击检测是本次 WAF 的主要额外成本。** 固定在 160 请求/秒时，完整 WAF 的 Edge CPU 用量在两端均约为关闭 WAF 时的 3 倍。仅 IP 匹配分别增加约 1.9 和 0.7 个 CPU 百分点。
- **JP-B 的吞吐损失可复现。** 在 8 × 16 对照下，完整 WAF 比关闭 WAF 少处理约 14% 的成功请求。关闭 WAF 后将并发从 8 × 16 增至 16 × 24，吞吐仍约 490 请求/秒，P95 却从两轮的 334–373 ms 升至 1,045 ms。
- **US-C 的吞吐差异随并发变化。** 在 8 × 16 对照下，完整 WAF 比关闭 WAF 低约 3%；在 16 × 24 单轮测试中顺序反转。固定负载下可明确看到其 CPU 与延迟开销，但不能据此给出稳定的吞吐损失比例。
- **继续定位吞吐上限时，优先对照访问日志持久化。** 三组都保留了逐请求加锁写入和 `sync_data()`。本次测到的是包含该路径的 Pages 吞吐平台；还需单独改变日志落盘方式，才能量化其影响。
